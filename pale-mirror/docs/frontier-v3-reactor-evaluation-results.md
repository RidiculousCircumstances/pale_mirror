# Reactor: результат изолированного эксперимента

Дата: 2026-10-29. [Согласованный план](frontier-v3-reactor-evaluation-plan.md).

**Решение: текущий Reactor-адаптер не принимать в производственный вычислительный
слой.** Он технически работает, но отдельного убедительного выигрыша библиотеки
над теми же зависимостями без библиотеки не получено. Дорогим осталось получение
самих входов. Переход к масштабному внедрению по этапу 6 не начат; основной и
масштабный серверы, их миры и установленные JAR не менялись.

Это решение о данном кандидате. Оно не доказывает непригодность Reactor для
потоков изменений, публикуемых владельцами данных, и не отменяет необходимость
исправлять широкие зависимости действующего вычислительного слоя.

## Что действительно проверено

Непроизводственный source set `reactorExperiment` в `pale-mirror-frontier` вызывает
настоящий `GoodsResourceValuation.assess`, а через него настоящий
`SupplyCapacityComposition.forValuation` со всеми семью зарегистрированными
производителями. Формулы, источники запасов, прогнозы труда и себестоимость не
переписаны для теста. Java 21.0.12+8-LTS; библиотека `reactor-core:3.8.8`.

Использован сохранённый **нативный checkpoint тяжёлой фазы**: 100 поселений,
3031 житель, канонический тик 439523, покрытая последовательность WAL 7454613.
SHA-256 бинарного snapshot:
`0e8a158534f7ec4deb05eca720f92f711a7328f636b2b4453ce235db49a1bb5d`.
Поздний хвост WAL не проигрывался: это точный образ checkpoint, не заявление
о полном восстановлении последней ревизии работающего сервера.

Из него через существующие именованные update API построены неизменяемые
офлайн-ветви: движение постороннего жителя, изъятие единицы чужого/местного
запаса, изменение рабочего модификатора, расписания и состояния здания станции.
Файлы исходного checkpoint не редактировались. Эти ветви не являются результатом
действия клиента или native acceptance.

| Вариант | Что исполнялось |
|---|---|
| A | Существующий production memo `GoodsResourceValuation.VALUES` и его настоящая функция, без изменений |
| B | Явный неизменяемый набор входов, сравнение с последним набором участника, та же функция |
| C | Тот же набор и функция, ограниченный реестр общих `Mono.cache`, результат через `CompletableFuture` |

Для A целый вектор цен читается из **действующего** private memo через диагностический
доступ: ровно тот же ключ и вычисление, что у `replacement`. Отдельно подтверждено
совпадение каждого элемента с публичным `replacement`. Это исключает искусственный
штраф A за сборку нового вектора циклом по публичным поэлементным вызовам.
Ранний пилот с таким циклом исключён из итоговых цифр.

Весь измеряемый A/B/C путь последовательный, в одном и том же JVM/thread.
Конкурентная проверка C использует отдельный host-owned executor с двумя потоками
и очередью 2. Это не замер параллельной пропускной способности и не новый worker
pool сервера. Default Reactor pools, Spring и Netty не используются.

## Прочитанные зависимости и цена проекции

`ValuationExperimentInputs` — диагностическая проекция из **одного** снимка,
не второй доменный владелец. Это полный консервативный read set данного среза,
а не минимальная семантическая версия каждого производителя.

| Владелец | Существенные данные в основании |
|---|---|
| Общая оценка | Идентичность bootstrap/правил/мира; явные party, policy, home; текущие ссылки цен для объявленных товаров |
| Запасы | Фактическое unclaimed по действующему общему отбору хранилищ, включая фильтры, custody, индивидуальные инструменты и claims |
| Труд | Местные профили и характеристики, life status, наличие миграции, расписание; правила труда/инструментов находятся в bootstrap |
| Пекарня | Доступные станции нужной capability, рецепт/топливо/work catalog; потенциальные работники |
| Поле | Местные lifecycle/cycle, факты pending-мутаций клеток, актуальные позиции подходящих складов, местные работники/агрономические правила |
| Добыча | Текущие местные deposit rows с материалами, клетками, prerequisites и development; потенциальные работники и определения инструментов |
| Автоматические станции | Доступные станции по capability, рецепты/топливо, текущие количества для выбора альтернатив ингредиентов |
| Индивидуальные изделия | Доступные станции и attended-рецепты Individual, потенциальные работники, work catalog |
| Attended stock | Доступные станции, stock-рецепты, местные количества и потенциальные работники |
| Лес | Объявленное знание леса, остаток по виду дерева, потенциальные работники и правила рубки |

Обычное движение тела не попадает в производственную возможность человека.
Текущие количества и допустимые позиции складов считываются через их настоящих
владельцев, поэтому динамическое хранилище не теряется за старой привязкой.
Отсутствующие станции/запасы/возможности также входят в проекцию; появление
меняет её, а не остаётся навечно закешированным отсутствием.

В проекции есть собственный shared directory месторождений: один обход при
смене корня deposits, затем местные строки для каждого запроса. Это **остаточное
ограничение**, не доказательство полностью инкрементального producer API.
Существующие owners также продолжают делать собственные индексные обновления.
На каждом запросе проекция всё ещё читает местные товары, жителей и клетки поля.
Lifecycle/cycle/deposit rows местами захватываются шире необходимого.

Никакого автоматического отслеживания чтений Reactor сюда не добавил.

## A/B/C: измеренные числа

Три прохода с ротацией порядка A/B/C после прогрева. В каждой строке 2700
запросов; ниже медианы. Для одного поселения последовательность из 27 снимков
повторяется 100 раз, для 100 поселений она проходит по всем участникам один раз.
Состав работы различается: эти две группы нельзя сравнивать как линейный тест
масштабирования одного и того же поселения.

| Поселений | Вариант | Запусков оценки | Изменений результата | Wall, мс | CPU thread, мс | Allocated, MB |
|---|---|---:|---:|---:|---:|---:|
| 1 | A | 2700 | 200 | 670.782 | 659.589 | 467.249 |
| 1 | B | 500 | 200 | 689.474 | 688.284 | 440.004 |
| 1 | C | 500 | 200 | 744.536 | 721.800 | 441.176 |
| 100 | A | 2700 | 101 | 442.015 | 437.876 | 351.195 |
| 100 | B | 106 | 101 | 403.233 | 390.287 | 278.060 |
| 100 | C | 106 | 101 | 359.653 | 358.840 | 278.942 |

Число A — число промахов настоящего top-level memo при данном порядке уникальных
снимков/участников, установленное по его ключу, **не** инструментированный счётчик
каждого внутреннего provider. B/C считают собственные фактические вызовы той же
функции. Внутренние действующие кеши сохранены у всех вариантов.

На 100 поселениях 2700→106 означает устранение 96.1% входов в верхнюю оценку,
но **не** ускорение всей симуляции в 25 раз. Выделение памяти B относительно A
снизилось на 20.8%; это фактические ThreadMXBean deltas, не heap occupancy и не
количество объектов. MB здесь десятичные.

Разброс CPU на 100 поселениях: A 374.5–441.3 мс, B 380.3–397.2 мс,
C 330.6–403.7 мс. Время C заметно снижалось по ходу проходов; JVM/JIT и общий
живой хост не позволяют выдать медиану за устойчивый процент выигрыша библиотеки.
Фоновая работа серверов не остановлена. В измеряемые окна не запускались наши
новые сборки, JFR или клиенты. CPU относится к измеряемому thread, не включает
GC/compiler threads и не является CPU всего процесса.

Стоимость capture на 100 поселениях занимает 91.5–93.7% wall B и 91.2–92.2%
wall C. В неё входят реальные обновления/чтения owner-индексов, сборка проекции
и её объектов. Вынос дорогого пересчёта «перед библиотекой» не засчитан как победа.

Отдельный контроль на **уже подготовленных настоящих входах**: 40 000 запросов,
100 реальных вычислений, остальные чтения равных оснований. Медианы трёх проходов:

| Вариант | Wall, мс | CPU thread, мс | Allocated, MB |
|---|---:|---:|---:|
| B | 117.220 | 111.679 | 42.533 |
| C | 111.391 | 109.061 | 54.730 |

CPU-диапазоны перекрываются: B 98.9–124.8 мс, C 107.9–118.6 мс. Убедительного
преимущества по времени нет. Дополнительное выделение памяти C — **28.7%**,
около 305 байт на запрос. В полном пути эта разница составляет лишь около 0.32%
между B и C: нельзя объявлять весь экономический расчёт на 29% дороже.

## Корректность и жизненный цикл

- Каждый ответ **всей** измеренной последовательности сравнен с настоящим A,
  включая промежуточные значения, а не только последнее состояние/счётчики.
  Сравнивается полный вектор объявленных товаров, не один хлеб.
- Движение постороннего жителя и чужое изъятие оставили местное основание равным.
  Местные запас, профиль, расписание и станция изменили основание. В этом checkpoint
  только отключение выбранного здания изменило численный результат; остальные
  существенные изменения были консервативными инвалидациями с равным ответом.
- Диагностический потребитель сравнивал векторы значений отдельно от request
  witness: 106 вычислений дали 101 изменение значения на 100 поселениях.
  Следующий тяжёлый торговый расчёт не подключён; его экономия не измерялась.
- Заблокированный barrier-ом настоящий расчёт разделяется подписчиками. Отмена
  одного не перезапускает его и не освобождает вычислительный permit до завершения.
- Смена нужного основания во время расчёта делает поздний ответ `STALE`, **даже
  когда новый запрос пока получает `WAITING_CAPACITY`**. Ожидание не превращается
  в отрицательное экономическое решение.
- Ветвь и база не смешиваются; eviction требует повторного настоящего расчёта.
  Ошибка поставщика доходит до caller; явный новый запрос после ошибки работает.
- Закрытие адаптера во время работы запрещает позднюю публикацию; последующий
  запрос получает `CLOSED`. Host executor не закрывается адаптером.

Пределы адаптера: 128 ключей в сравнении, 2 незавершённых вычисления, 256 подписчиков;
в конкурентном различающем сценарии специально 1 ключ/1 вычисление/8 подписчиков.
Измеренные пики в сравнении C: 100 ключей, 1 подписчик и 1 вычисление; на выходе
pending=0/running=0. Конкурентный сценарий: пик 3 подписчика, 3 общих обращения,
3 отклонённых устаревших ответа, 1 ожидание ёмкости. Позднее закрытие проверено
отдельно на финальном исходнике.

Supplier освобождается после исполнения, реестр не сохраняет его целый world root
в готовом `Mono`. Число активных захватов ограничено work permits; кеши настоящих
доменных функций сохраняют прежние собственные ThreadLocal-границы. Драйвер
намеренно удерживает свои входные 27 офлайн-снимков. Точный retained heap/GC-паузы
не измерялись; количественный heap claim из этих структурных границ не делается.

Адаптер — request-driven shared Mono с явными основаниями, **не** полноценный
push-граф экономики. Отрицательное рыночное решение, появление новой заявки,
деньги, срок, согласие, команда и геометрия остаются в настоящем торговом контуре:
его защитные проверки не ослаблены. Два существующих набора
`GoodsProcurementTransportTest` (3 теста) и
`GoodsParticipantOpportunityAdviceTest` (4 теста) прошли; это сохранность старой
границы, не доказательство новой интеграции графа в торговлю.

## Практический вывод

В этом срезе не доказана окупаемость новой библиотеки. Готовый механизм разделения
подписки удобен, но библиотека не убрала получение stock/worker/field projections
и не владеет freshness/admission/retention. Этап 6 требует положительного
решения по этапу 5. Оно не получено, поэтому native-интеграция не выполнялась.

Следующий полезный срез — **публикуемые владельцами локальные неизменяемые факты
производственной возможности**, обновляемые по затронутым данным и общие для
потребителей. Тогда сравнение происходит до повторного сбора товаров/жителей/клеток,
сохраняется полное отрицательное знание, а дорогой downstream зависит от значения,
не от каждого нового world root. Это отдельная реализация: в рамках эксперимента
такой второй framework не строился. Выбор push-адаптера можно повторно проверить
на этой реальной границе; принимать Reactor сейчас оснований недостаточно.

Устойчивые 20 канонических тиков/с в тяжёлой фазе не доказаны и этой работой
не объявляются. Навигация, GC, canonical validation и широкие рыночные fence
остались за пределами изменённого среза.
