# Сквозная причинная трассировка задержек симуляции

## Цель и границы

Дать измеренную картину продвижения часов: от попытки пройти логический интервал
через действия, расчёты, доставку результатов и WAL к следующему продолжению.
Расширяем существующие FrontierV3DelayTrace/JFR и tools/performance. Никакой второй
системы состояния, очереди, часов, планировщика или runtime-телеметрического сервиса.
События выключены без записи; диагностика не меняет исполнения и разрешений.

## Результат

Один bounded JFR конвертируется в машинный отчёт, интерактивную локальную временную
диаграмму и граф причинных связей. Длительности — монотонные наносекунды с показом
миллисекунд; канонические тики/долг отдельно. CPU и параллельные длительности не
суммируются с эксклюзивной таблицей wall time. Две величины качества: баланс
разбиения всего окна и объяснённая причинная часть. Неразобранное время не исчезает.

Узлы имеют реальные diagnostic IDs и владельца/тип/исходную revision; разделяем
проход действия, advisory, exact preparation, worker slice, уведомление, приём
результата и запись. Общая задача может иметь несколько наблюдателей. Нет связи
по похожему имени потока или близости времён. Незавершённые/потерянные связи и
обрезанные границы записи сохраняются явно.

## Реализация

1. Дочитать существующие эмиттеры/доставку и исправить недостающую причинную связь
   между worker notification, coalesced ready-turn и следующей owner attempt.
2. Явно связать clock turn/attempt/action/async task; отметить пополнение бюджета
   и поступление времени, чтобы не растягивать старое состояние ожидания через
   фактическую смену условия. Добавить подтверждение приёма WAL receipt владельцем.
3. Один streaming JFR export и один offline анализатор: граф, partition/gates,
   nested exclusive owner stages, completeness, loss, task lifecycle, WAL members,
   GC pause/stall overlays и stacks. Runnable unknown остаётся неизвестным.
4. Локальная timeline с выбором мира/масштаба/интервала/задачи; исходный граф и
   JSON доступны без внешнего сервера или загрузки данных в сторонний сервис.
5. Проверить overlap/shared dependencies/missing/cancel/retry/data-loss/capture-edge
   на коротких детерминированных записях; JFR lifecycle test проверяет реальные
   уведомления и read-only семантику. Не добавлять тесты производительности по времени.
6. Коммит, frozen package, штатная доставка MAIN/SCALE с сохранением MAIN мира.
   Снять ограниченный сквозной trace на100towns и выдать конкретную сводку, включая
   неизвестный остаток и предел влияния самой записи. Не объявлять это оптимизацией
   или доказательством20 ticks/s.

## Реализованный срез и проверка — 2026-10-29

Production commit `af28fd3adbae5b19844916b11df899644a36f8e8`: расширен существующий
JFR observer, связаны реальные уведомления и coalesced delivery, clock turn /
advance / action / async task, подтверждения WAL и существующий batch timer.
Очередь уведомлений сохраняет тот же единственный atomic ticket, теперь вместе с
диагностическим контекстом. Диагностика не выбирает действия и не меняет бюджет.
Формат мира, правила экономики и навигационные алгоритмы не менялись.

Один анализатор заменил прежний текстовый Java-report; Java остаётся streaming
нормализатором JFR. После проверки на реальной записи исправлены границы окна:
берутся закрытые chunk headers JFR v1/v2, а не начало старого ThreadPark.
Неполные/неизвестные файлы отклоняются. Producer artifact и исходники анализатора
имеют отдельные идентификаторы/хеши. Время ожидания не приписывается CPU по native
stack samples: они могут попадать в блокирующие epoll/fsync.

Проверено: 47 выбранных Java-тестов (runtime, WAL, preparation, ready delivery и
реальный JFR), 11 детерминированных проверок анализа, guardrails, frozen JAR и
packaged verification. Полный набор тестов не объявляется зелёным: два ранее
зафиксированных посторонних NeoForge отказа не исправлялись в этом срезе.
Финальная timeline открыта настоящим Chrome: поиск точного ID, переход по связи,
масштабирование, перетаскивание и окно 900×600 проверены, JS-ошибок нет. MCP browser
не имел executable; использован установленный Chrome через CDP, затем закрыт.

MAIN и SCALE штатно остановлены с native save, обновлены одним frozen artifact
и проверены скриптами pack-репозитория. Оба мира сохранены. MAIN service
`far-frontier-v3-live.service`, world `frontier-v3-r281-cold-atomic-20261028`;
SCALE `far-frontier-r31-scale-audit.service`, world `scale-r31-schema313-seed126`.

30.001715057 с. Необъяснено 3.343202942 с (11.1437%): внутренний пробел владельца,

о замкнутости наблюдаемых ссылок; `causalClosureComplete=false` сохраняет этот пробел.
Никакого объявления «объяснили всё».

Внутри инструментированного владельца: validation 4.215105 с, schedule planning
3.917095, physical projection 2.053617, allocation 1.721943, reduction 1.504075,
transaction 1.285816, persistence 0.266092. Это эксклюзивные интервалы вложенных
фаз, их можно сложить внутри соответствующего бюджета, но нельзя добавлять к
повторно включающим их внешним spans.

Среди exact clock gates: goods opportunity 1.911156 с, actor movement 1.244437,
cultivation 0.857183, extraction 0.747077, hauling 0.708802. Следовательно, один
торговый расчёт не объясняет всё отставание в этом окне. Большая сумма worker CPU
тоже не равна ожиданию часов: наблюдаемые парные CPU-интервалы навигации 51.899464 с
на двух потоках, advice 26.506566, exact 6.856514, WAL 0.101769; CPU владельца в
измеренных turns 14.333064 с. Это разные перекрывающиеся потоки, не части таблицы
wall time. На границах записи непарные CPU-интервалы не выдумываются.

Конкретная цепочка для поиска в UI: exact ID `1994`,
`frontier.actor.movement.progress`, `resident:92-8`. Очередь 0.853987 мс,
worker wall 205.242150 мс, затем ready notification → ready-turn `2091` → owner
turn `2093` → advance `2097` → observing action `2098`. Совокупное эксклюзивное
ожидание именно этой задачи — около 162.46 мс: остальная часть перекрылась с
другой работой владельца. Граф сохраняет несколько наблюдателей и scope joins;
это не чистый DAG и не алгоритм longest path.

Часы 532913 → 533067 за наблюдаемые 29.419172094 с: 5.234682 тика/с. За тот же
интервал поступило 603 host ticks, долг 351 → 800; 603−154=449, расхождение баланса
0. Это измерение инструментированного текущего мира, не сравнение производительности
с прежним checkpoint, не доказательство замедления от самого tracer и не20 TPS.
Общая задача20/no-debt остаётся открытой. Накладные расходы записи не измерены
парным прогоном, поэтому количественный overhead не заявляется.
